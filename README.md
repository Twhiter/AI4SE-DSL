# DSL easy

A Langium language with a VS Code extension and a browser editor

| Package | What it is |
|---|---|
| `packages/language` | grammar, parser, validator and tests; and the Z3 checks, where a list or queue holds at most its capacity (150 by default: `capacity` of the checks' options), a list keeping duplicates and a queue its order, and a Then's effects on one apply in the order written, removing an element or dequeuing one needing it there (`src/z3-vocabulary.ts`) |
| `packages/extension` | VS Code extension (language server) for `.easy` files: the language's errors and, without them, the Z3 checks, as the browser editor runs them, in the Problems panel; and a DCR graph panel ('DSL easy: Show DCR graph', the button on an `.easy` file's title bar) with the graph of the `.easy` file shown last. The setting `easy.listCapacity` is the lists' and queues' capacity in its checks (150 by default) |
| `packages/dcr-view` | the DCR graph viewer of [dcr-js](https://github.com/hugoalopez-dtu/dcr-js) (MIT), copied and changed to show initiators and observers, to draw relations in DCR Solutions' notation, and to let events and relations be dragged; and its view of DSL easy's DCR graphs (`src/graph-view.ts`), laid out by elkjs, for the VS Code panel |
| `packages/dcr-js-adapter` | a DSL easy model as DCR.js editor XML, laid out by elkjs, for the DCR page of `legal-dcr-frontend` (its `COMPONENT.md`): `toDcrJsXml(model, { fixInclusion })`. A data property is an activity with a variable, in the nesting Data, which has a condition to itself, so that its activities are never executed (their values change only by setValues); a state is an activity of the role Robot with a Bool variable, in the nesting States, included and pending, with a response to itself, and computed from the state's Declarative specification (its `computation`: DCR.js's tokens, as its import of a DCR Solutions expression gives them; an action's status, which that import does not read yet, as a tuple of the action's element and the status); an action's Givens are a condition from Data to it, guarded by `not(g₁ or g₂ …)`, each `gᵢ` its states (`busy = true`) and its data: the action waits while none of them holds (a model without data properties has an activity `placeholder` in Data for it); an action with one input and no output is an activity with the input's variable; one with more inputs, or with outputs, is a nesting holding the nestings Input and Output, an activity with a variable for each; an action's activities start included and pending as its `Initially available` and `Initially pending` say (neither without them), but an action that no include relation goes to starts included, whatever it says, as it could otherwise never happen (the fixer: `fixInclusion`, on by default); 'is set to' is a setValue. Variable names have `_` for spaces; a data property's has its entity's name before it only when another entity's data property has the same (`Printer_speed`), a state's its entity's name when another entity's state, a data property or an action has the same (`Printer_idle`), an input's or output's its action's name when any other variable has the same (`submit_child_age`, while the data property stays `child_age`). DCR.js has no list values and no word for no value, so lists, queues and 'is undefined' are left out (`src/graph.ts`), but not by the DCR Solutions adapter |
| `packages/dcr-solution-adapter` | the same graph as DCR Solutions XML, as dcrgraphs.net exports a graph (`dcr solution examples`): `toDcrSolutionXml(model, { title, fixInclusion, marking })`. A data property is an event with its entity as role, in the nesting Data, from which the Givens' conditions go, guarded by `not(…)`, as in `packages/dcr-js-adapter`; a state is an event of the role Robot in the nesting States, a choice of true or false that its computation gives: what the state's Declarative specification says, an action's status as `print@executed`, `print@pending` or `print@included` (available), `print is enabled` as what its enabled specification says and `print@included`; it starts included and pending, with a response to itself (`dcr solution examples/DCR computation.xml`); an action is an event with its initiators (roles) and observers (read roles), with the input's value when it has one input and no output; one with more inputs is a form holding them, one with outputs a form holding the nestings Input and Output. An event's id is what the FEEL expressions name it by: a variable's name (as in `packages/dcr-js-adapter`), or an action's. 'is set to' is an update, its When the guard and its value the value (`dcr solution examples/DCR update.xml`); an action's several for the same property are one, their Whens joined with or and their values as `if … then … else …`; strings are in single quotes; 'is undefined' is `= null` ('is not undefined' `!= null`), and each data property starts with no value, null (`dcr solution examples/DCR null.xml`). A list or queue is an event with a list value, starting as `[]` (`dcr solution examples/DCR list.xml`), and what is said about it is written with list functions: `list contains(jobs, 'a')`, `count(jobs) = 0`, `count(jobs) >= 150` for full (the capacity, `capacity`); a Then's effects on it, in their order, are one update: `append(jobs, 'a')`, `remove(jobs, index(index of(jobs, 'a'), 1))` (guarded by `list contains(jobs, 'a')`), `remove(waiting, 1)` for a dequeue (guarded by `count(waiting) > 0`, the dequeued element being `index(waiting, 1)`), `[]`. Data and then States are above the actions, Data's data properties a row for each entity's; the actions are laid out as in `packages/dcr-js-adapter`, with the relations between them only. By default an event starts as the model says: a data property included, a state included and pending, an action as its `Initially available` and `Initially pending` say, or included by the fixer, as in `packages/dcr-js-adapter`; events in a form always start included (`marking`). The browser editor exports it; showing it there is future work |
| `packages/web` | browser editor: Monaco, the language and Z3, no server; its Problems panel lists the errors and the Z3 checks, and its DCR graph view shows the DCR page of `legal-dcr-frontend`, given the XML of `packages/dcr-js-adapter` after every check; the Export menu in the menu bar at the top downloads the document, once it has no errors, as DCR Solutions XML (`packages/dcr-solution-adapter`, for dcrgraphs.net) or as DCR.js XML (`packages/dcr-js-adapter`). A checkbox, Fix inclusion, in the DCR graph view and in the Export menu, turns the adapters' fixer on and off for both (on by default, kept in the browser); a field, List capacity, in the Problems panel's header, sets the lists' and queues' capacity for the checks and the DCR Solutions export (150 by default, kept in the browser) |
| `packages/dsl-controller` | DSL controller: the model of a document and the tools that read and change it, the checks (validation and Z3), and plans of changes tried on a copy; not tied to the chatbot or to an agent SDK, so an MCP server could offer the same tools |
| `packages/chatbot` | the chatbot (OpenAI Agents SDK) on the DSL controller's tools, and the document server that the editor's chat pane talks to, with the agents' prompts, skills and session logs. A change the chat agent suggests is checked before the user sees it: it proposes it as options (`propose_changes`), the planning agent plans each at once, and only those whose plans run with no new errors are offered, as buttons that show their plans to approve or reject, with nothing planned again (`src/agent.ts`); a change the user asks for is planned (`plan_changes`). A plan can be approved in part, each change having a toggle: without a reason, the steps that make just the changes kept run (`selectSteps` in `packages/dsl-controller`) and change the document when they do; otherwise, or with a reason, the planning agent plans them again, fixing what they miss, for the user to approve. Other choices, such as what to do next, it offers as buttons too (`offer_choices`, `src/options.ts`; `OPTIONS=off` in `.env` turns those off) |
| `packages/dsl-mcp` | an MCP server on the DSL controller's tools, for clients such as Codex and Claude Desktop (`codex mcp add dsl-easy -- node <path>/packages/dsl-mcp/src/main.ts`): `create_dsl` (the domain, in text) makes a folder `packages/dsl-mcp/documents/<id>` (`dsl.easy`, `domain.txt`, `log.jsonl`) and gives only the id, which every other tool takes as `dsl`; the read tools read the document, and it changes only through plans (`simulate_plan`, which also gives what the plan changes as a diff, and `apply_plan`). Every call and its answer, errors included, is a line of `log.jsonl`; the server keeps no state between calls |

## The web chatbot

The browser editor's chat pane talks to the chatbot's document server (`packages/chatbot`), which runs the agents.
After the setup above:

1. Start Docker: the agents read their skills in a container, one per conversation (not needed with `SKILLS=off`).
2. Write `packages/chatbot/.env` (git ignores it):
   ```
   OPENAI_API_KEY=…    # the endpoint's key
   OPENAI_BASE_URL=…   # the endpoint (OpenAI's Responses API, or one compatible with it)
   OPENAI_MODEL=…      # optional: gpt-5.4 by default; a claude-… model works too
   SKILLS=on          # optional: no skills, and no Docker
   OPTIONS=on         # optional: no buttons for the choices that are not changes
   WEB_PORT=5174      # optional: the browser editor's port, and
   DOCUMENT_PORT=1234 # the document server's: others, for a second checkout (a worktree) beside this one
   LIST_CAPACITY=150  # optional: the most elements a list or queue holds in the agents' Z3 checks (packages/dsl-controller;
                      # for the MCP server, in its environment)
   ```
3. Build the DCR page once, and again after changing `legal-dcr-frontend` (it needs Yarn):
   ```bash
   npm run dcr-page
   ```
4. From the root folder, start the document server (ws://localhost:1234) and the browser editor together:
   ```bash
   npm run dev
   ```
5. Open http://localhost:5174, describe the domain, and chat. Each browser tab is a session, log fies are in
   `packages/chatbot/logs/session-<id>.md` (and `.json`).
